# 90. Whole-array operations on results are engine commands over a typed expression tree evaluated in Rust

Date: 2026-11-17

## Status

Accepted as step S3 (plan item N1) of the productivity plan (`docs/NYX2_PRODUCTIVITY_PLAN.md`, section 3b). **The number 90 is the one the plan reserves for "per-element numerics are formulas evaluated in Rust" and is provisional**: take the next free ADR number at merge and renumber this file, the index row and the code comments. This record covers level N1 (whole-array operations) and the tree that levels N2 to N4 build on; N2 (text formulas, material values, `where`, vectors) is added below (step S5); N2b (tensor entries, a wavelength, a weight, boundary integrals) is step S5b; N3 (tracing script functions) is step S6, added below; N4 (a code generator) amends it if it lands.

## Context

A researcher or an agent wants numbers computed from a field: the integral of `|E|^2` over the core, the confinement factor, the largest stress, the field along a line, the overlap of two modes. Before this step the only way was `result_field`, which returns up to 2000 sampled node-averaged values, and a loop of arithmetic written by the caller. In an interpreted script such a loop is 10 to 100 times slower than Rust and, worse, it reads values that were averaged over the cells and sampled, so the number it gets is not the integral of the field the solver made.

## Decision

* **Eight commands, one implementation** (`nyx_engine::reduce`): `field`, `field_op`, `integrate`, `extremum`, `probe`, `line_cut`, `overlap` and `confinement`. They are ordinary engine commands (read access), so the MCP server lists them as tools, a script (S4) calls them, and the window's Reduce form in the Results tab calls the very same commands (`App::reduce_now`; the test compares the line it shows with the command's number).
* **A handle is a value, not an id.** `field` returns `{"field": "Ex", "physics": "ems", "solution": 0}`; arithmetic builds `{"op": "mul", "args": [a, b]}` (`add sub mul div neg abs abs2 re im conj sqrt pow`); numbers are `{"num": x}` or `{"num": [re, im]}`; a bare string is a field of the request's `physics` and `solution`. The engine keeps no handle table, so a handle has no lifetime and cannot go stale in the engine: it is read against the stored result each time and the answer says `stale` and `age_s` (as `result_field` does). The tree is `femcore::fieldexpr::Tree` (complex values, leaves are numbered slots, every operation written out so the order of the floating-point operations is fixed by that file).
* **A leaf reads the field the solver made.** A name is first looked up among the per-cell fields of the solution (`cell_fields`: `Ex`, `uz`, ..., complex when the solve is, not averaged over cells), then among the node-averaged flat fields of `result_info` (`T`, `|E|`: real, one value per dof). Both are Lagrange P1 or P2 interpolants on the cells of the mesh the result was solved on. **A stored result keeps that mesh** (`Stored.model`), so a result is read on its own cells whatever the project's mesh is now (a changed element size makes the result stale, not unreadable).
* **The rule (what N2, N3 and N4 must reproduce bit for bit).** Integrals use the degree-4 symmetric rule of `femcore::fem::quad_rule` (6 points on a triangle, 14 on a tetrahedron), exact for the product of two P2 fields; an integrand of higher degree carries the quadrature error. At each point every leaf is `sum_a N_a(q) v_a` (local node order, starting from 0.0) and the tree is evaluated on those values. A cell adds `vol * sum_q (w_q * f_q)`; cells are summed in blocks of 2048 consecutive cell numbers in cell order and the blocks in block order, so the sum has the same bits for any thread count (`tests/reduce.rs` runs it on 1, 3 and the pool's threads). The reference loops in `tests/reduce.rs` are written on the raw arrays of the result and agree **to the bit** with the commands; the closed forms (polynomials of degree 2 integrated by Gauss-Legendre over boxes) agree to 1e-9.
* **Measure.** The plane measure (area in 2D, volume in 3D) is the default. `revolution: true` multiplies the integrand at each quadrature point by `2 pi r` (r is mesh axis 0, the mesh must be 2D) for bodies of revolution. It is an explicit argument, echoed in every answer, because the engine does not know which physics is axisymmetric; when a result's study name says `axisym` and the argument is absent, the answer carries a note.
* **Maxima are nodal.** `extremum` takes the largest or smallest real value at the nodes of the cells of a region (vertices, and edge midpoints of a P2 mesh), not over the interpolant; it says so, and returns the cell, the local node and the point. A complex expression has no order and is refused with the advice to wrap it in `abs`, `abs2`, `re` or `im`.
* **`probe` and `line_cut`** find the cell of a point with a uniform grid of the cells' boxes and interpolate in that cell. Points are in mesh axes (a 2D mesh: x then z of the wafer; 3D: x, y, z). A point outside the mesh answers `inside: false` and a null value, not an error; a point on the face between two cells is read in the cell with the lowest number (the fields are not averaged, so the two cells can differ by the discretisation error).
* **`overlap` and `confinement` have no material weight.** `overlap` returns the complex integral of `sum_k conj(a_k) b_k` over a region, the two norms and the coefficient `|overlap|^2 / (norm_a norm_b)` (0 to 1, Cauchy-Schwarz); `a` and `b` are a field or a list of components. `confinement` returns the integral of `sum_k |c_k|^2` over a region divided by the same over the whole mesh. The energy or power fraction needs the permittivity at each point, which is N2 (material values in formulas); until then the commands say what they computed in `meaning`.
* **Where the tree lives.** The plan says N1's handle arithmetic builds the formula tree of N2, extending `femcore::expr`. That evaluator is real-valued and has no fields; making it complex and giving it field leaves is the substance of N2. So S3 adds the typed tree `femcore::fieldexpr` (complex, field leaves) and N2 adds a text parser that produces the same tree and moves `expr::Expr` (initial values from `x y z`) onto it. Until then there are two small evaluators in `femcore`; the gate for N2 is that a formula and a handle give the same bits.

## N2: text formulas (step S5, 2026-11-18)

A string in an `expr` is now a formula: `abs(Ex)^2 * eps_r`, `where(z > 0, p, 0)`, `inner(E, E)`. `femcore::formula` parses it once into the same `fieldexpr::Tree` that handles build, so a formula and a handle are one request with one evaluator, and the gate is that they give the same bits (`tests/reduce.rs::a_formula_equals_the_handle_form_to_the_bit`: `abs(Ex)^2 + abs(Ez)^2` equals the handle `add(pow(abs Ex), pow(abs Ez))`, and `Ex * Ez` equals `mul`, both to the bit; the loop on the raw arrays agrees).

* **Grammar** (the module comment of `formula.rs` is the reference): numbers (`2j` is imaginary), `pi`, `e`; `+ - * / ^` (also `**`), comparisons, `and or not`; `abs abs2 re im conj sqrt exp sin cos arg` on complex values; `log log10 tan sinh cosh tanh atan step min max atan2` and a non-integer power on real values; `where(cond, a, b)`, which evaluates only the branch that applies (so `where(x != 0, 1/x, 0)` is safe). A power with a whole constant exponent from -16 to 16 is repeated multiplication, which is exactly what the handle `pow` builds. Nothing else parses: no input can run code, name a file or call anything not listed. Nesting is limited to 64 levels.
* **Real-only operations are checked, not guessed.** `Tree::check` runs once per request, before any point, and refuses a comparison, a `where` condition, `log`, `tan`, `min` and so on whose operand is complex, naming the formula and advising `abs`, `abs2`, `re` or `im`. A formula never silently takes the real part.
* **Names** are resolved by the engine (`reduce::Namer`) in this order: the coordinates `x y z` (wafer axes; `y` is 0 on a cross-section; interpolated from the nodes like a field); a field of the result (a plain string that is exactly a field name still means that field, as before; a name that is not an identifier, such as `|E|` or `Re Ex`, goes in backticks inside a formula); a vector (`E` when the solution has two or three of `Ex Ey Ez`; `dot`, `inner` which conjugates the first, `cross`, `norm`, `norm2`, `E.x`); a **material value** by descriptor name (`eps_r`, `rho`, ...; `eps` and `mu` mean `eps_r` and `mu_r`). `material("rho")`, `region("Si")` and a backticked `ems:1:Ex` say what they are when a name is ambiguous or belongs to another physics or solution. An unknown name lists the names there are.
* **Material values are what the solver read.** They come from the problem of the physics as `nyx_physics::decode::materials_by_label` builds them for the solve (library materials, inline numbers, the optical model at the wavelength of the study), one scalar per cell, **constant over the cell** (not interpolated, so a region indicator or a material is the same number at every quadrature point). They are read from the project's current problem and the result's own mesh: if the materials changed since the solve the answer carries `stale: true`. A property that is a tensor in some material of the mesh (an anisotropic or rotated `eps_r`) is refused rather than read as its scalar default. `region("name")` is 1 in the cells of the region and 0 elsewhere.
* **An expression of numbers only** (`1`, for an area) uses the mesh of the default result.
* **`femcore::expr` is unchanged.** The plan says N2 moves `expr::Expr` onto the new tree. It does not: `expr` is the real grammar of geometry and initial fields that `geom::expr` copies (ROUGH_SPOTS R06), the two are held equal by `tests/expr_grammar.rs`, and moving one side would break that test or force `geom` onto `femcore`. The formula grammar is a superset kept separate, and the gate "the existing `expr_grammar` tests unchanged" holds because the file is untouched. Two evaluators remain in `femcore`: the real one for geometry and initial fields, the typed one for results.
* **Not done in S5, built in N2b below:** line and surface integrals; tensor material values; a material dispersion at another wavelength. Still not done: a formula inside a worker.

## N2b: tensor entries, a wavelength, a weight, boundary integrals (step S5b, 2026-11-19)

What S5 left out, built on the same tree. The formula box of the Reduce form (Results tab) is a text field whose content goes to `integrate` and `extremum` unchanged, so the window and a script give the same number.

* **Tensor entries.** A tensor property has plain names for its entries in wafer axes: `eps_r_xx`, `eps_r_yy`, `eps_r_zz`, `eps_r_xy`, `eps_r_xz`, `eps_r_yz` (and `k_*`, `alpha_*`; `eps_zy` is `eps_r_yz`; `eps` and `mu` keep meaning `eps_r` and `mu_r`). The entries come from `Materials::cell_tensor`, the call the solvers make, with the crystal orientation applied, so an isotropic material is `v I` and a mesh with both kinds reads correctly. The frame is the global (wafer x, y, z) one of `cell_tensor`; `section::local_tensor`, which reorders to (x, z, y) for the kernels, is not used. The plain `eps_r` is still refused on a mesh where some material is a tensor, and its message names the entries. Gate: r-plane sapphire at 57.6 degrees (a non-zero yz entry), every one of the nine entries equals the library's `optical_permittivity` for the same angles to 1e-9 of the area-weighted value.
* **`wavelength`** (metres), an optional argument of every reduction: where the material values of a dispersive model are read, default the study's. The fields stay those of the solve; it is an explicit what-if on the materials, not a re-solve. The leaf records it, so two wavelengths in one formula are two leaves.
* **`weight`** of `confinement`: a real formula that multiplies the integrand (`eps_r` gives the energy fraction). Without it the tree, and so the bits, are those of S3; with it the answer equals the ratio of two `integrate` calls to the bit.
* **Boundary integrals** (`integrate` with `boundary`, in place of `region`). Decisions:
  * Only named boundaries: an outer boundary (the labelled facets of the solver mesh, edges in 2D and triangles in 3D, by `LabelResolver::boundaries`, the same text the conditions use), or an interface `a|b` between two regions. The solver mesh keeps no facets for an interface, so for a name that reads `a|b`, has no facets and whose two parts are regions, the faces are those shared by a cell of `a` and a cell of `b`, which is what the geometry names `a|b` (all its pieces). An arbitrary path or surface is not integrated; `line_cut` samples a line.
  * **An interface has two sides and the fields are discontinuous across it** (`Ex`, `eps_r` at Si/SiO2). A facet with two adjacent cells needs `side`, a region name: the facet is read in its cell that belongs to the region, and the answer says which side. A facet with one cell (an outer boundary) needs none; a facet with two cells and no `side`, or with both cells in `side`, is an error that names the boundary. Nothing picks the lowest-numbered cell.
  * **The normal** `nx`, `ny`, `nz` (wafer axes, unit length, constant on a facet) points out of the chosen cell. These names exist only in a boundary integral and are an error elsewhere. A flux is `dot(F, [nx, ny, nz])`.
  * Rule: the facet rule of `fem::facet_rule` (3-point Gauss on an edge, degree 5; the degree-4 triangle rule on a face); each point is mapped to the barycentric coordinates of the chosen cell, where the leaves are interpolated exactly as in a volume integral. A facet adds `measure * sum_q (w_q f_q)`; facets are summed in blocks of `BLOCK` consecutive facets in facet order, so the bits do not depend on the thread count.
  * `revolution` is supported on a 2D (r, z) mesh: the integrand and the measure are multiplied by `2 pi r` at each point. The answer reports `measure` (length, area; with `revolution` the surface of revolution) and the number of facets.
  * Gates: the length of a known boundary (expr `1`) and the area of one in 3D; a closed form on a uniform field (flux through a face is `F . n A`); the divergence theorem on a smooth field: the integral of `dot(F, n)` over the whole outer boundary equals the area integral of `div F`.

## N3: a script function becomes a formula (step S6, 2026-11-19)

`nyx.integrate(expr=integrand, region="Si")` with `def integrand(p): ...` calls `integrand` **once**, with a symbolic point, records what it does as formula text, and sends that text to the engine, where it is the N2 formula of the same words. Nothing new reaches the engine: no command, no argument, no change to `engine_commands`. The traced function is a way to *write* a formula, so the bit-identity gate of N2 carries over unchanged: the engine sees text and parses it with the one parser.

* **Where it runs.** In the script worker, as Python (a prelude fed before the user's script, generated by `nyx_script::trace::prelude` from `Engine::catalog()`). Monty runs the function, so loops with a fixed number of steps, helper functions, comprehensions and local variables all work, as in JAX. The function is called once per command, not per element (a counter in the test says 1).
* **The symbolic value** is an instance of a small class `Sym` that holds formula text. `+ - * / **`, unary minus, `abs`, and their reflected forms build text with **every operation parenthesised and operand order kept** (`2 * e.x` is `(2 * E.x)`, never `(E.x * 2)`; `1 - e.x` is `(1 - E.x)`), so the parsed tree is the tree of the same expression written by hand (the parser makes no node for a parenthesis). A number is written with Python's `repr` (shortest text that reads back as the same double; an integer stays an integer, so `x ** 2` stays the repeated product the parser makes of `^2`). A bool is 1 or 0; a number that is not finite, a complex number or any other value (text, a list) is an error that says what a traced function computes with.
* **The argument of the function** is one value, `p`, the point: `p["E"]` is the vector field `E` (components `.x .y .z` are `E.x`, ...), `p["eps_r"]` a material value, `p["Ex"]` a field, `p["nx"]` a normal; `p.x p.y p.z` are the coordinates. `p["name"]` is a name of a formula; the engine resolves it, so an unknown name gets the engine's own message listing the names there are. **Deviation from the plan** (`def integrand(e, eps)`): Monty gives a function no `__code__` and no `inspect`, so a parameter cannot be bound by its name; the plan's form is one `p` with names as keys.
* **Functions** are the prelude's: `where(c, a, b)`, `sqrt exp sin cos log log10 tan sinh cosh tanh atan atan2 step re im conj arg abs2 minimum maximum dot inner cross norm norm2 material region`, and conditions `lt gt le ge eq ne land lor lnot`. `abs(x)` is Python's, through `__abs__`. They accept symbolic values and plain numbers.
* **Where Monty stops us (1.6.0, measured).** A class's `__bool__`, `__lt__` and its siblings, `__ne__` and `__getattr__` are not called by Monty: `if sym:` takes the true branch, `not sym` is False, `sym > 0` is a `TypeError` of Monty's own, and `sym != 0` is the bool `True`. The plan's rule (a branch on a symbolic value is an error that says `where(...)`) cannot be kept by the runtime for these. What the runtime does keep: `==`, `float()`, `int()`, `round()`, `[..][sym]` and iterating raise our error that names `where(...)` (the dunders Monty does call).
* **A static guard keeps the rule.** Before a script runs (and in `nyx check`) `nyx_script::trace::guard` parses it (`ruff_python_parser`, the parser Monty uses, pinned the same) and finds the functions passed to a `nyx.` call (a name of a `def`, or a `lambda`, directly or in a list), with the functions they call by name. In them it follows which names depend on the point (the parameter, anything assigned from an expression that mentions one, loop and comprehension variables over one, the parameters of a helper called with one, including through containers) and refuses an `if`, `while`, `a if c else b`, `and`, `or`, `not`, a comprehension condition, `assert` or a comparison whose test mentions one, and `math.` calls on them, with the line, the text of the rule and the `where(...)` spelling to use. A branch on something that does not depend on the point (`if USE_CORRECTION:`, `for k in range(3)`) is allowed, as in JAX. Limit, stated in the contract: the guard is a syntactic over-approximation; a value hidden from it (a symbolic value stored in a structure the guard does not follow, a function chosen at run time) is not seen, and then `if sym:` takes the true branch. **Paul may prefer a Monty that dispatches `__bool__`** (an upstream change) over this guard; the guard then becomes a second line of defence.
* **Contract.** `script_api` 1.1 (provisional, additive): the traced-function form, the names, the guard. The stub gains the prelude's names so the static check knows them. The user's script is fed after the prelude as its own feed, with the prelude fed without the type check, so traceback line numbers are the user's.

## Not in this decision

* A code generator (N4).
* Convergence of an integral under refinement (a reduction reads one result on one mesh).
* Reductions in a worker process: they read the result the parent holds and take about as long as reading it.
* Maxima of the interpolant between nodes.

## Consequences

* `engine_commands` gains eight commands and `result_info` gains `cell_fields` (additive); `mcp_tools` gains eight tools (additive). Provisional versions 1.12 and 2.8. N2 changes only descriptions (provisional 1.14 and 2.10). N2b adds arguments (`boundary`, `side`, `wavelength`, `weight`) and so is 1.15 and 2.11, still provisional; nothing is removed.
* `Stored` holds the mesh model of its result, so a result keeps its mesh alive until it is replaced.
* `nyx check` treats the eight commands as readers of a result.
* N3 changes no engine command and no MCP tool: the engine receives the same formula text. It adds a Python prelude to every script run (a few milliseconds), the names `where`, `sqrt`, ... `trace`, `region`, `material` to a script's globals (a script may still use them as variable names; the stub declares them as `Any`), the `ruff_python_parser` crates (the parser Monty already links) to `nyx-script`, and `script_api` 1.1 (provisional).
